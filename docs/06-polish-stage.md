# P 阶段：体验打磨（M9 之前）

> 状态：**进行中**（2026-11-20 立项，用户拍板单列一个阶段）。本文定义的是「怎么调」，不定义「要什么」——
> 交互规格与验收标准仍以 `02` 为准，协议与数据口径仍以 `03` 的决策为准。
> 台账：`docs/polish-log.md`，全局唯一的问题入口。
> **编号说明**：不叫 M8.5。`02` §6 里已经有一个 **M8-5**（无 Key 行内引导，已并入 M7-6），
> 再叫 M8.5 会让后续会话把两件事混成一件。这个阶段用 `P` 开头，内部循环用 P1、P2……编号。

## 1. 为什么不列清单

前面八个阶段靠「验收标准」收口：写清楚什么算完，做完划掉。打磨期反过来——改进的判据不是标准，是**比较**：
比刚才顺、比官方像、比上一版不别扭。比较需要两样东西：能复现的现场，和能并排看的证据。缺了这两样，
每一轮的结论都会退化成「我感觉好像好一点」，改多了以后连「好一点」是相对哪一版都说不清。

所以这个阶段立的不是清单，是**装置**：把「发现问题」和「验证一次改动」的成本压到足够低，
问题自己浮出来。装置四件，见 §3–§6；循环一轮的实际流程见 §2。

还有一条隐含前提：**这个阶段的输入只能来自真的用**。不是读代码想出来的、不是照官方截图比出来的。
所以第一轮的第一件事是把基线拍下来（§8），然后拿着手机按脚本走（§4）。

## 2. 循环

一轮 = 一个批次，期望 1–2 天，不做长跑。

| 步 | 做什么 | 时长 |
|---|---|---|
| ① 走 | 装当前构建，按 §4 的体验脚本从头走一遍，遇到不对的**只记不改** | 15–20 分钟 |
| ② 记 | 把发现写进 `docs/polish-log.md`，含复现步骤与截图/录屏文件名 | 5 分钟 |
| ③ 批 | 按「同一处代码」归并，不按「同一句抱怨」归并；一批取 3–5 条 | 5 分钟 |
| ④ 改 | 一次只动一个方面（交互、展示、动效三者不混），改完装、重走受影响的脚本片段 | 半天到一天 |

第四步的「一次只动一个方面」不是洁癖。三类改动会互相掩盖症状：间距改小了，动画看起来变快了；
动画变慢了，滚动看起来更卡。混在一起改，出了新问题无法归因，只能整体回退。

**提交粒度**：一条台账项一个提交，提交标题带台账编号，例如
`fix(chat): 消息到达时不再抢滚动（P-014）`。这样任何一次调整看起来不对，可以单独回退那一条，
而不是回退一整轮。禁止出现标题叫「打磨」的大提交。

**每轮结束**在 §11 的轮次记录表里加一行：改了什么、证据在哪、留下什么。

## 3. 装置一：台账

`docs/polish-log.md`，只追加不删行（关闭时改状态列）。一行一条，字段固定：

| 字段 | 写法 |
|---|---|
| 编号 | `P-001` 起连续递增，永不复用 |
| 方面 | 交互 / 展示 / 动效（只选一个，混着写说明还没想清楚） |
| 现象 | 用户视角看到什么，一句话，不写推测 |
| 复现 | 最短动作序列，能照着做出来的程度 |
| 证据 | `captures/p-001-*.png` 或 `.mp4`，没有证据的条目视为未确认 |
| 严重度 | P0 / P1 / P2 / P3，定义见下 |
| 状态 | 待复现 / 已确认 / 修复中 / 待回归 / 关闭 / 推迟 |

严重度不看「改起来难不难」，只看「用起来多难受」：

- **P0** 明显做错或阻塞日常使用（点了没反应、内容错位、崩）
- **P1** 每次用都会注意到的别扭（滚动抢位、动画卡顿、对齐不齐）
- **P2** 偶尔注意到（某个角落的间距、某种组合下的换行）
- **P3** 想到才在意（几乎不影响使用的细节）

处置节奏：P0 当轮清掉；P1 本轮或下轮必须动；P2 攒到三条以上再一起改；P3 冻结后进待办，
不当场改——打磨期的失控几乎都来自「顺手把 P3 也改了」。

一个条目连续两轮没人动，就把它降级或关闭。台账里长期挂着的待办等于没有台账。

## 4. 装置二：体验脚本

十六条，每轮重走，其中最后一条是横屏与分屏——它属于「序列」里最容易被漏掉的那一类。交互问题几乎只在**序列**里出现：单点看每一步都对，连着做就别扭。
这份脚本也是 M9 冒烟清单的底稿，做完这一步 M9-5 只剩补发行相关项。

| # | 动作序列 | 期望 |
|---|---|---|
| 1 | 冷启动 → 直接进上次的会话 → 上滑看历史 → 回到顶部 | 没有白屏跳动，列表停在原位不回弹 |
| 2 | 新建会话 → 发一句短问 → 等回答流式写完 | 首字出现不迟于 1 秒，正文只增不回缩 |
| 3 | 发一个长回答请求 → 写到一半上滑 → 等写完 → 点「回到底部」 | 上滑后不抢滚动，按钮出现时机不早不晚 |
| 4 | 发一个含代码块的问题 → 代码块边流边看 → 展开全部 → 收起 | 流式期间不折叠，展开收起后列表不跳位 |
| 5 | 回答完成后连点「复制」两次 → 切到另一个会话 → 长按粘贴 | 图标变勾 1.5 秒，粘贴内容完整无多余空行 |
| 6 | 长按正文 → 拖动选择手柄 → 复制选区 | 手柄跟手、放大镜不遮挡、选区跨段不错位 |
| 7 | 打开带引用的回答 → 点角标 → 来源页 → 返回 | 角标位置贴段末，来源页返回后列表停在原位 |
| 8 | 点「重新生成」→ 生成中途点「停止」→ 再点「继续生成」 | 三个动作的状态不互相污染，操作栏一直可用 |
| 9 | 发一条带图片的消息 → 点开大图 → 双指缩放 → 返回 | 缩放手感正常，返回后缩略图不闪 |
| 10 | 点麦克风 → 按住说话 → 松手 → 等识别结果发出 | 录音态与键盘态切换不闪，识别结果不丢字 |
| 11 | 打开抽屉 → 长按会话 → 置顶 → 删除 → 取消 → 再删 | 长按菜单不遮挡，取消后列表顺序不变 |
| 12 | 设置 → 外观 → 深色 → 回聊天页 → 再切回浅色 | 切换不重建会话、滚动位置保留、无黑屏闪 |
| 13 | 设置 → 字体大小 → 特大 → 回聊天页看代码块与表格 | 只放大正文，代码块不溢出、表格可横向滚动 |
| 14 | 输入框长按 → 全选 → 剪切 → 粘贴 → 发送 | 操作行与输入区高度过渡自然，不留空档 |
| 15 | 打开「用法与费用」抽屉 → 点标签展开释义 → 关闭 → 立刻再打开 | 抽屉动画可被打断，重复打开不叠加、不闪 |
| 16 | 旋转屏幕（或在分屏里）→ 聊天页 → 输入框 → 发送 | 输入内容不丢、键盘不遮挡、列表不跳位 |

**怎么记**：走的时候手机连电脑，发现不对立刻 `adb shell screencap` 或 `screenrecord`，
文件名按 `captures/p-<编号>-<一句话>.png` 存。没证据的条目进台账时状态写「待复现」。

## 5. 装置三：样本集

展示类改动极容易按下葫芦浮起瓢：为宽表格调字号，窄表格就散了；为长代码块调行高，段落就松了。
所以固定一份语料，每次改展示规则，整份过一遍，而不是只看手头那条。

语料放在 `app/src/debug/assets/samples/`（仅 debug 打包，不进正式包）：

| 文件 | 压什么 |
|---|---|
| `01-mixed-script.md` | 中日英混排、全角标点、表情符号、行内代码与粗体交错 |
| `02-long-paragraph.md` | 超长段落，验证行高、两端对齐、首行缩进观感 |
| `03-wide-table.md` | 六列宽表格，验证横向滚动与表头固定 |
| `04-long-code.md` | 六十行 Kotlin，验证折叠、横向滚动、着色与行号观感 |
| `05-nested-list.md` | 三层嵌套的有序/无序/任务列表混合 |
| `06-inline-heavy.md` | 超长链接、行内公式、行内代码连续出现 |
| `07-short-reply.md` | 一个字与一句话的极短回答，验证气泡最小宽度与操作栏 |

用法（待实施）：debug 构建里加一个「样本预览」页，按序号列出这七份，点开用 `TcMarkdown` 渲染在一个
300dp 宽的假气泡里（就是现在的气泡宽度），顶部可切「全宽」，用来直接判 P-001 那条要不要改按比例。
不走「复制到输入框再发送」——那样只会得到一条用户消息，看不到助手侧的渲染；也不走 `adb input text`，
中文与表情走命令行会被吃掉。预览页与调参面板共用同一个 debug 入口，都放 `app/src/debug/`，release 不打包。

## 6. 装置四：动效令牌与调参面板

### 6.1 替换前的现状（2026-11-20 扫的结果，已完成替换，留作对照）

全工程 13 处动画规格，全部是 `tween`，**没有一处用 spring**：

| 时长 | 处数 | 用途 |
|---|---|---|
| 120ms | 1 | 操作栏淡出 |
| 180ms | 4 | 操作栏淡入、折叠箭头、Crossfade、淡入 |
| 200ms | 5 | 用量抽屉淡入淡出、抽屉横移、操作栏两处 |
| 520ms | 1 | 朗读中的三根跳动竖条（循环） |
| 未写曲线 | 12 | 只有朗读竖条显式写了 `FastOutSlowInEasing`，其余走 Compose 默认 |

结论：数值本来就比较集中（120/180/200），所以**统一成令牌的代价很小**；真正缺的是曲线与命名，
以及「新代码不许写裸数字」这条规矩。现在改比以后改便宜。

### 6.2 令牌（已落地）

`core:designsystem/TcMotion.kt`。数值不另造一套，直接以 `02 §16` 的规格为准：

| 令牌 | 值 | 用在哪 |
|---|---|---|
| `Quick` | 120 | 状态反馈与退场淡出：图标变勾、菜单遮罩、朗读竖条的错峰 |
| `Fade` | 150 | 内容淡入：思维链正文 |
| `Base` | 180 | 通用：操作栏、思维链标题切换、菜单遮罩退场 |
| `Panel` | 200 | 布局移动与展开：左右抽屉、思维链高度 |
| `Sheet` | 240 | 底部抽屉上滑（`02 §16`） |
| `MenuIn` | 120 | 长按菜单进场 |
| `MenuOut` | 90 | 长按菜单退场（比进场短一档，收得干脆） |
| `Ambient` | 520 | 循环动画：朗读中的跳动竖条 |

曲线三条：`Standard` = `cubic-bezier(0.4, 0, 0.2, 1)`（即 `02 §16` 的那条）、`Decelerate` = `LinearOutSlowInEasing`、
`Emphasized` = `cubic-bezier(0.2, 0, 0, 1)`。

规则四条：

1. 新代码不许出现裸数字时长或裸曲线，一律取令牌。
2. 进场用 `Standard`，退场用 `Decelerate` 且比进场短一档——退场慢了会显得拖沓。
3. 同一个元素进出场的时长必须成对登记，改一个必须改另一个。
4. 循环动画（朗读竖条、光标闪烁）不进通用档，集中在 `TcMotion` 里命名，避免满工程找 520。

> 为什么不是「快/中/慢」三档：`02 §16` 里抽屉是 200、底部抽屉是 240、思维链高度是 200 配 150 淡入、
> 消息插入是 180。硬凑三档就得改规格里的数字，等于为了整齐去动手感。按用途命名的代价是令牌多几个，
> 好处是每一个都能对上规格里的一行。

替换 13 处的活已在 2026-11-20 完成，一次改完、一次验证，不留半新半旧。

### 6.3 调参面板（设计，待实施）

仅 debug 构建存在的调试面板，长按「关于」页的版本行两秒打开。目的只有一个：
**把试错成本从「编译安装一分钟」压到「拖一下滑杆」**。Compose 没有可用的热重载，
一个下午能试的版本数就直接被编译时间卡死。

参数（只调数值，不开关功能）：

| 组 | 参数 | 范围 | 现值 |
|---|---|---|---|
| 消息 | 气泡最大宽度 | 240–420dp | 300dp（固定值） |
| 消息 | 相邻消息垂直间距 | 0–24dp | 实施时读现值 |
| 消息 | 列表左右内边距 | 8–24dp | 实施时读现值 |
| 代码块 | 折叠阈值行数 | 8–40 行 | 20 行 |
| 代码块 | 圆角 | 0–16dp | 实施时读现值 |
| 排版 | 段落间距 | 0–16dp | 6dp |
| 排版 | 标题上/下间距 | 0–24dp | 12–14 / 6dp |
| 排版 | 列表项间距 | 0–12dp | 3dp |
| 动效 | 全局时长倍率 | 0–3× | 1× |
| 动效 | 禁用所有动画 | 开/关 | 关 |
| 诊断 | 显示布局边界 | 开/关 | 关 |
| 诊断 | 显示实时帧率 | 开/关 | 关 |

实现约束三条，都是为了避免面板污染产品：

1. **参数集中**：`core:designsystem` 提供 `TcTuning`（不可变数据类）+ `LocalTcTuning` 组合局部，
   默认实例的值就是现在的代码值；debug 构建把它替换成可编辑实例并挂面板，release 构建不替换。
   **不允许**在业务代码里出现 `if (BuildConfig.DEBUG)` 的分支散点。
2. **面板是草稿纸**：某个值调定以后，写回源码常量并删掉面板项。长期保留双份真相
   （面板默认值与代码常量各说一套）比没有面板更糟。
3. **不做发布开关**：面板里不出现「是否显示时间戳」这类功能开关。功能开关会让 debug 与 release
   出现两套行为，验证过的样子在正式包里不存在。

## 7. 三类改动的验收证据

这三方面不只是内容不同，**验收方式也不同**，混着看就会自欺：

| 方面 | 证据形式 | 判据 |
|---|---|---|
| 交互 | 录屏，按 §4 脚本走完整序列 | 每一步都符合期望，没有多余步骤，可被打断 |
| 展示 | 同一屏幕截图，浅深两套，与基线并排 | §5 样本集全部不退化，关键间距用工具量不靠眼估 |
| 动效 | 慢放录屏（系统动画倍率 5×）+ 帧耗时 | 不掉帧、可被反向打断、退场比进场短 |

动效必须慢放看。正常速度下，「曲线不对」和「时长不对」在肉眼里是同一件事；把系统动画时长倍率调到
五倍或十倍，问题一眼就能分出来。打断测试也不能省：连点、动画中途返回、旋转、切后台——
过不了这几关的动画在真机上会显得廉价。

帧耗时不看感觉，用 `adb shell dumpsys gfxinfo top.tbpdt.tinychat framestats` 或调试面板里的帧率读数列，
和 §8 的基线数字比。

## 8. 基线

进 P 阶段前先拍一份，不然所有比较都只能靠印象。一条命令：

```powershell
pwsh -File scripts/capture-baseline.ps1
```

脚本做四件事，产物全部落在 `captures/baseline-<日期>/`（已 gitignore）：

1. **九个界面的浅色与深色截图**：会话列表、聊天页（含长回答）、抽屉、模型选择、设置首页、
   用量抽屉、服务商列表、关于页、输入区聚焦态。步骤是引导式的——脚本提示「现在把界面切到 X，按回车」，
   按一下截一张；不做坐标点击，避免改版后整份脚本失效。
2. **四段动效录屏**：抽屉滑出、操作栏出现、代码块展开、流式首字。
3. **冷启动耗时**：`am start -S -W` 跑三次取中位数，记 `TotalTime`。
4. **滑动帧率**：`gfxinfo` 重置 → 引导滑动聊天页十秒 → 取 50/90/95/99 分位与 janky 比例。

同时写一份 `manifest.txt`：机型、系统版本、屏幕密度与刷新率、应用版本号、采集时间。
密度与刷新率必须记——同一个动画在 60Hz 与 120Hz 上的观感不同，换个设备再比就没有意义。

## 10. 边界

这个阶段**不碰**下面这些，碰到了就是走错了阶段：

- 协议、报文、数据表结构、导入导出格式（属于 `03` 的决策范围，改一次要连带迁移与兼容）
- 依赖版本与新增依赖（值得加的单独开一轮讨论，混在打磨里会引入无法归因的回归）
- 新功能（「纯对话模式」「自定义温度」这类在 `03` 里已经明确否决，不要借打磨复活）
- 品牌与文案口径（文案口径按决策 39，本阶段只补 `docs/copy-review.md` 里还没过的行）

允许碰的：间距、圆角、字号与行高的**展示**微调，动画曲线与时长，交互顺序与反馈时机，
文案的具体措辞（不改变口径）。
